## 플랫폼 — 프로토타입에서 유통까지

**이 문서는 결정문이 아니라 선택지 문서다.** 지금(1인 + 에이전트 팀, three.js
웹 프로토타입, v0.4)을 기준으로 갈래마다 값과 대가를 적고 권고를 하나 골랐다.
실제 착수는 오너 판단이다. **v1.0 이전에는 아무것도 재구성하지 않는다** — 이 문서가
말하는 것은 "지금 두 줄이면 되는데 나중엔 두 주가 되는 것"을 미리 가려두는 일뿐이다.

### 지금이 실제로 어떻게 생겼는가

읽고 확인한 사실만 적는다. 추측은 없다.

| 축 | 지금 |
|---|---|
| 백엔드 | `node:http` + `node:sqlite`, 의존성 0개 ([`server/index.js`](../../server/index.js), [`server/db.js`](../../server/db.js)) |
| 서버 권위 | 세이브·시드 발급·기록 셋뿐. 이동·물리는 클라이언트가 전부 시뮬레이션 |
| 세이브 저장소 | sqlite `saves` 테이블 (player_id PK) — 서버가 죽어도 [`Api.ts`](../../src/net/Api.ts)가 localStorage로 조용히 대체 |
| 플레이어 식별 | 계정 없음. `crypto.randomUUID()` 를 브라우저 localStorage에 두고 그걸로 식별 |
| 유산(Legacy) | **서버에 없다.** `localStorage['eden:legacy:v1']` 에만 있다 ([`Legacy.ts:22`](../../src/gameplay/Legacy.ts)) |
| 스키마 버전 | `SAVE_VERSION = 1` 상수 하나뿐 ([`server/index.js:25`](../../server/index.js)). 버전이 다르면 서버는 409로 거절만 하고 업그레이드하지 않는다 |
| 세이브 필드 확장 방식 | 실제 마이그레이션이 아니라 **옵셔널 필드 + 각자 기본값**으로 버텨왔다 ([`SaveState.ts`](../../src/gameplay/SaveState.ts) 의 `warmth?`, `fertility?`, `unlocked?` 등 8개) |
| 기록 검증 | `POST /api/runs` 는 `days >= 1` 만 확인한다. UUID 형식이 맞는 플레이어 ID면 누구든 임의의 기록을 넣을 수 있다 ([`server/index.js:131`](../../server/index.js)) |
| 요청 제한 | 본문 크기 상한(1MB) 뿐, 레이트리밋 없음 |
| CORS | `access-control-allow-origin: *` — 개발 편의로 전부 열어둠 |
| 빌드 | `tsc --noEmit && vite build` — 정적 산출물 하나. 서버는 번들되지 않고 raw Node로 별도 실행 |
| 자산 | **전부 절차적 지오메트리.** `public/` 은 비어 있고 glTF·텍스처 로더가 코드 어디에도 없다 (렌더링 레이어는 분리되어 있음 — [07-risks.md](../design/07-risks.md)의 완충책) |
| 배포 형태 | 없음. itch.io/Electron/Tauri 어느 쪽도 아직 손대지 않았다 |

## 1. 유통 형태

| 갈래 | 요구하는 것 | 이 게임에 맞는 정도 |
|---|---|---|
| 순수 웹 (itch.io/자체 호스팅) | 없음 — `vite build` 산출물을 그대로 올린다. 자동 업데이트는 "새로고침"이 전부 | 지금 `Api.ts`의 오프라인 폴백이 이미 이 형태를 전제로 짜여 있다. 설치 없이 바로 검증 가능 |
| Steam (Electron/Tauri 래핑) | 코드사이닝, Steamworks SDK 연동, 스토어 심사, 별도 업데이트 채널(Steam이 대신 해줌) | 발견성·신뢰도는 얻지만 지금 규모(프로토타입, 로우폴리 도형)에 심사·서명 절차를 얹을 이유가 아직 없다 |
| 둘 다 | 위 둘의 합 + 두 배포 채널의 버전 동기화 | v1.0 이후, 웹에서 반응이 확인된 다음 결정할 문제 |

**권고: 지금은 순수 웹 유지.** `npm run build` 산출물이 이미 itch.io에 바로 올라간다 —
추가로 할 일이 없다. Steam으로 갈 때는 Electron보다 **Tauri**를 먼저 검토해라 — 웹뷰
기반이라 three.js 코드를 거의 그대로 쓰면서 설치본이 Electron(~100MB대 Chromium 번들)보다
훨씬 작다(러스트 툴체인은 필요). 이 판단은 v1.0에서 아트가 들어와 실제 씬 크기와
성능이 나온 뒤에 하는 게 맞다 — 지금은 근거가 될 데이터가 없다.

**지금 해두면 값싼 것:** 없음. 빌드 파이프라인이 이미 정적 산출물을 낸다.

## 2. 세이브와 계정

지금 구조: `sqlite`(서버 권위, 온라인일 때) + `localStorage`(오프라인 대체) +
익명 UUID(계정 아님). **문제는 유산이다** — [`Legacy.ts`](../../src/gameplay/Legacy.ts)는
서버에 전혀 올라가지 않는다. 브라우저 데이터를 지우거나 기기를 바꾸면 지금까지 계승해온
조감도·기록 조각·되살린 흙이 **전부** 사라진다. 세이브(sqlite)는 이미 기기 독립적인데
유산만 예외로 남아 있다.

**이행 경로가 핵심이다.** 나중에 로그인 계정을 붙일 때 지금 플레이 중인 사람의 진행을
안 끊기게 하려면, "익명 UUID를 계정에 나중에 매다는" 순서여야지 "계정을 만들어야
플레이할 수 있다"로 뒤집으면 안 된다. `player_id`는 그대로 두고 `account_id`를
nullable로 매핑하는 테이블 하나를 얹는 정도로 충분하다 — 익명 플레이어는
`account_id = NULL`로 계속 돌고, 로그인하면 그 시점에 매핑이 채워진다.

**권고:**
1. 유산을 서버로 옮기거나(가장 정직한 해법), 최소한 export/import(JSON 다운로드·업로드) 기능부터 갖춘다 — 계정 시스템 없이도 기기 이동 문제의 절반을 해결한다
2. 실제 계정(이메일/OAuth)은 유통 직전에 붙인다 — 그때까지는 붙일 게 없다(순위표만으론 계정 필요성이 약하다, 4번 참고)

**지금 해두면 값싼 것:** `saves`/`runs` 테이블에 `account_id` nullable 컬럼을 미리
넣어둔다. 지금은 항상 NULL이지만, 나중에 계정을 붙일 때 `ALTER TABLE`과 기존 행
백필을 피할 수 있다 — 컬럼 하나 vs 운영 중인 sqlite 파일 마이그레이션.

**그때 가서 해도 되는 것:** OAuth 로그인 플로우, 계정 연동 UI, 실제 유산 이전 로직.

## 3. 스키마 버전과 마이그레이션

**지금 없다.** `SAVE_VERSION`은 서버에 상수 하나(`1`)뿐이고, 버전이 다른 세이브는
그냥 409로 거절한다 — 업그레이드 경로가 없다. 실제로 스키마가 늘어난 이력은
[`SaveState.ts`](../../src/gameplay/SaveState.ts)에 흩어진 옵셔널 필드 8개
(`warmth?`, `bindings?`, `fertility?`, `unlocked?`, `guide?`, `restored?`,
`worldSeasons?`, `archive?`, `vault?`, `masts?`, `surveyed?`, `storage?`)로
버텨온 것이다 — 필드를 옵셔널로 추가하고 읽는 쪽에서 각자 기본값을 채운다.
이건 "필드가 늘 뿐 구조가 안 바뀌는 동안"만 통하는 방식이다. 필드 이름이 바뀌거나
중첩 구조가 바뀌면 이 패턴은 깨진다.

**필요한 최소 형태:** 명시적 `schemaVersion` 필드 + 버전별 순수 업그레이드 함수를
체인으로 잇는 것 (`v1→v2→v3`, 각 함수는 이전 버전 객체를 받아 다음 버전 객체를 반환).
서버는 저장하기 전에 항상 최신 버전으로 올려서 저장하거나, 읽을 때 그 자리에서
업그레이드한다. 클라이언트 로컬 세이브에도 같은 함수를 그대로 재사용한다 —
포맷이 같으므로 마이그레이션 로직도 하나면 된다.

**이 규모에 별도 마이그레이션 프레임워크(Drizzle 등)는 과하다.** 테이블이 둘뿐이고
스키마가 JSON 블롭(`payload TEXT`) 하나에 몰려 있어서, 버전 필드 + 함수 체인 정도가
정확히 필요한 만큼이다.

**지금 해두면 값싼 것:** 흩어진 옵셔널 필드 기본값 채우기를 **지금 한 곳**
(`migrate(state)` 같은 단일 함수)으로 모아두는 것. 지금은 필드 8개라 파일 하나
훑으면 되지만, v0.6·v1.0에서 계속 늘면 "이 필드가 어디서 기본값을 받는지"를
코드 전체에서 찾아야 하는 작업이 된다. 지금 모아두면 나중에 버전 분기만 얹으면 된다.

**그때 가서 해도 되는 것:** 실제 구조 변경을 요구하는 마이그레이션(필드 이름 변경,
중첩 구조 변경) — 지금은 그런 변경이 없으니 미리 만들 로직이 없다.

## 4. 권위와 치트

`POST /api/runs`는 클라이언트가 보내는 `days`·`plots`·`harvests`·`gathered`를
그대로 믿는다. UUID 형식만 맞으면 브라우저 콘솔에서 `fetch`로 임의의 기록을
명예의 전당에 올릴 수 있다.

**순위표(명예의 전당)가 없다면 서버 검증은 거의 값이 없다** — 싱글플레이 세이브를
자기가 조작해도 손해 보는 사람은 본인뿐이다. 이 근거를 분명히 적어둔다: **진짜
안티치트(서버가 게임 로직을 재시뮬레이션해서 검증)는 이 아키텍처의 핵심 결정 —
"이동과 물리는 서버로 보내지 않는다" — 을 뒤집는 것과 같다.** 그건 순위표 하나를
지키자고 싱글플레이 조작감을 왕복 지연에 넘기는 것이라 배보다 배꼽이 크다.

**권고: 최소 타당성 검사만 넣는다, 그 이상은 하지 않는다.**
- `POST /api/session`이 발급한 시각을 서버가 기억해뒀다가, `POST /api/runs`가
  왔을 때 "실시간 경과 대비 `days`가 물리적으로 가능한 범위인가"만 확인한다
  (하루가 실시간 15분이므로 상한 계산이 간단하다)
- 그 이상(리플레이 검증, 행동 로그 대조)은 순위표에 상금이나 경쟁적 의미가
  생기기 전까지는 비용 대비 효용이 없다

**지금 해두면 값싼 것:** 위 경과시간 상한 체크 — 세션 발급 시각 하나를 저장해두고
비교하는 한두 줄이다. 지금 넣으나 나중에 넣으나 코드량은 같지만, **지금 넣으면
sqlite에 이미 기록이 없으니 소급 검증이 필요 없다.** 유통 후에 넣으면 그때까지
쌓인 순위표 데이터가 전부 무검증 상태로 남는다.

**그때 가서 해도 되는 것:** 정교한 부정행위 탐지, 행동 로그 기반 리플레이 검증 —
순위표가 실제로 경쟁적 의미(시즌, 상금, 방송 등)를 갖게 될 때.

## 5. 운영

지금 에러 수집·크래시 리포트·통계가 전혀 없다.

**권고: 최소한만, 외부 서비스는 아직 붙이지 않는다.**
- 클라이언트 전역 에러 핸들러(`window.onerror`/`unhandledrejection`)가 잡은
  예외를 `server/index.js`에 엔드포인트 하나(`POST /api/errors` 정도) 추가해서
  보낸다 — `player_id` 없이도 동작하게 만들어 개인 식별 없이 "무엇이 죽었는지"만 모은다
- Sentry 같은 SaaS는 이 규모(1인 프로토타입)에 아직 과하다. 무료 티어로 되긴 하지만
  외부 의존과 계정 관리가 늘어나는 만큼, 자체 sqlite 테이블 하나로 충분한 동안은
  거기 붙일 이유가 없다
- 개인정보는 원칙적으로 **아무것도 모으지 않는다.** 지금 있는 `player_id`도 UUID일
  뿐 계정에 연결되기 전까지는 사람과 매핑되지 않는다 — 이 성질을 유지한다

**지금 해두면 값싼 것:** 특별히 없다. 지금은 플레이어 수 자체가 적어 에러를
사람이 직접 재현해서 잡는 게 더 빠르다 — 수집 파이프라인을 지금 깔아봤자
쌓일 데이터가 없다.

**그때 가서 해도 되는 것:** 원격 에러 전송, 대시보드, 익명 플레이 통계
(어느 날 가장 많이 죽는지 같은 것) — 유통 후 실제 플레이어가 생겼을 때.

## 6. 자산·빌드 파이프라인

지금 자산은 전부 절차적 지오메트리다 — three.js 프리미티브와 인스턴싱으로
코드가 직접 굽는다. `public/`은 비어 있고 glTF·텍스처 로더는 어디에도 없다.
로드맵상 로우폴리 아트 교체는 **v1.0**에 잡혀 있다([05-roadmap.md](../design/05-roadmap.md)).

v1.0이 오면 필요한 것:

| 필요 | 상태 |
|---|---|
| glTF 로딩 | `three` 패키지 안에 `GLTFLoader.js`가 이미 있다 — **새 의존성이 필요 없다** (`node_modules/three/examples/jsm/loaders/`) |
| 메시 압축(Draco/meshopt) | 로우폴리라 폴리곤 수가 애초에 적을 가능성이 높다 — 실제 자산이 들어와서 용량이 문제가 될 때 판단 |
| 텍스처 압축(KTX2) | 위와 동일 — `KTX2Loader.js`도 이미 `three` 안에 있다 |
| 캐시버스팅 | Vite가 빌드 시 파일명에 해시를 붙여 기본 제공한다 — **이미 공짜** |
| 로딩 화면/진행률 | glTF 로더가 붙는 시점에 같이 필요해진다 |

**권고: 지금 파이프라인을 미리 깔지 않는다.** 자산이 없는 지금 로더를 연결해봤자
검증할 대상이 없다 — 렌더링 레이어가 이미 분리되어 있다는 것(07-risks.md의
완충책)만으로 충분한 준비다. `GLTFLoader`·`KTX2Loader`가 이미 `three` 안에 있으므로
"의존성을 추가하는" 결정 자체가 필요 없다는 것만 미리 알아두면 된다.

**지금 해두면 값싼 것:** 없음.

**그때 가서 해도 되는 것:** `GLTFLoader` 연결, `public/models/` 디렉토리 구성,
압축 여부 판단(자산 용량이 나온 뒤), 로딩 화면.
